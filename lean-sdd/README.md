# lean-sdd

`lean-sdd` は、新規アプリ開発で **軽量SDD + AI実装** を行うための Codex Skill です。

重い設計書を最初から作り込むのではなく、次に実装する小さな垂直スライスに必要な仕様だけを定義し、受け入れ条件を確認してから実装します。

## 目的

このSkillの目的は、バイブコーディングの速度を保ちながら、次の問題を減らすことです。

* 仕様が曖昧なまま実装される
* AIが要求外の機能を追加する
* 技術選定の理由が残らない
* 受け入れ条件と実装がずれる
* テストや検証が後回しになる
* ドキュメントとコードがすぐ乖離する

## 基本方針

* Big Design Up Front はしない
* アプリ全体を最初から詳細設計しない
* 次に作る機能だけを軽量Spec化する
* ユーザー価値を持つ垂直スライス単位で実装する
* Specを作ってから実装する
* 受け入れ条件を観測可能にする
* 最小差分で実装する
* 不要な抽象化や将来用の空実装を作らない
* 実装後にSpec、コード、テストの対応を確認する

## 対象

このSkillは、次のようなケースで使います。

* 新しいWebアプリを作る
* 新しいモバイルアプリを作る
* 新しいCLIや小さなツールを作る
* アイデアからMVPを作る
* 次の機能を仕様化して実装する
* 仕様、実装、テストの整合性を確認する

既にある程度完成しているプロジェクトの整理や保守には、別Skillの `project-maintenance` を使います。

## モード

### shape

アプリのアイデアを整理し、MVPと垂直スライスに分解します。

通常は以下のファイルを作成または更新します。

* `docs/product.md`
* `docs/roadmap.md`

アプリケーションコードは変更しません。

使用例:

```text
$lean-sdd shape

複数台の車を管理し、給油、整備、車検の履歴を記録できる
個人向けWebアプリを作りたい。
まずMVPを整理してください。
```

### start

新規アプリの初期開発を開始します。

プロダクト定義、技術判断、最初のSpecを作り、最初の垂直スライスだけを実装します。

使用例:

```text
$lean-sdd start

個人向けの車両整備記録アプリを作りたい。
技術スタックは Next.js、PostgreSQL、Prisma を使います。
最初の垂直スライスを仕様化して実装してください。
```

### slice

次の機能スライスを仕様化し、実装し、検証します。

使用例:

```text
$lean-sdd slice

ユーザーが車両を登録できる機能を実装してください。
```

### change

実装済み機能の要件を変更します。

既存Specを先に更新してから、コードとテストを変更します。

使用例:

```text
$lean-sdd change

整備記録の走行距離を任意から必須に変更してください。
既存データへの影響も確認してください。
```

### check

プロダクト定義、ロードマップ、Spec、実装、テストの整合性を確認します。

原則としてファイルは変更せず、不一致と最小の修正案を報告します。

使用例:

```text
$lean-sdd check
```

## 作成される主なドキュメント

### `docs/product.md`

プロダクトの方向性を記録します。

主な内容:

* 解決する問題
* 対象ユーザー
* 提供価値
* MVPの範囲
* MVPに含めないもの
* 主要ユーザーフロー
* 成功条件
* 前提
* 未確定事項

### `docs/roadmap.md`

MVPを垂直スライスに分解して記録します。

悪い分け方:

* DBを作る
* APIを作る
* UIを作る

良い分け方:

* ユーザーが車両を登録できる
* ユーザーが整備記録を保存できる
* ユーザーが整備履歴を確認できる

### `docs/decisions.md`

現在有効な技術判断を記録します。

例:

* 言語
* フレームワーク
* DB
* ORM
* 認証
* 状態管理
* テスト方針
* デプロイ方法

各判断には、短い理由を残します。

### `docs/specs/*.md`

機能ごとの軽量Specを記録します。

基本構成:

```md
# Feature name

## Status

draft / accepted / implemented / verified

## Purpose

何を実現するか。

## User story

誰が、何をしたいか。

## Scope

今回含めるもの。

## Non-goals

今回含めないもの。

## User flow

ユーザー操作の流れ。

## Acceptance criteria

- Given ...
- When ...
- Then ...

## Constraints

制約や前提。

## Errors and edge cases

エラーや境界条件。

## Test approach

どう検証するか。

## Assumptions / Open questions

仮定と未確定事項。
```

### `docs/adr/*.md`

重要な技術判断だけを記録します。

ADRを作るべきケース:

* 後から変更するコストが高い
* 複数の有力な選択肢がある
* セキュリティやデータ整合性に関係する
* プロジェクト全体に長期的影響がある

軽微な実装判断ではADRを作りません。

## 運用フロー

基本の流れは以下です。

```text
1. shape でMVPと垂直スライスを整理する
2. start で最初のSpecと実装を作る
3. slice で次の機能を1つずつ追加する
4. change で既存機能の仕様変更を扱う
5. check でSpec、実装、テストの整合性を見る
```

## 垂直スライスの考え方

`lean-sdd` では、技術レイヤー単位ではなく、ユーザー価値単位で作業を分けます。

例えば、車両管理アプリの場合:

```text
Slice 1: ユーザーが最初の車両を登録できる
Slice 2: ユーザーが整備記録を登録できる
Slice 3: ユーザーが整備履歴を一覧できる
Slice 4: ユーザーが次回車検日を確認できる
```

各スライスは、必要に応じてUI、API、DB、テストを含みます。

## 完了条件

1つのスライスは、以下を満たした場合のみ完了とします。

* Specが存在する
* 受け入れ条件が明確である
* 実装が受け入れ条件を満たしている
* 受け入れ条件に対応するテストまたは手動検証がある
* lint、型チェック、ビルドなど必要な検証が通っている
* ドキュメントと実装が一致している
* 未解決事項とリスクが記録されている

## 禁止事項

* MVP全体を一度に実装しない
* 受け入れ条件なしで実装しない
* 要求されていない機能を追加しない
* 将来使うかもしれない抽象化を作らない
* 空の将来用モジュールを作らない
* 不要な依存関係を追加しない
* 不要なマイクロサービス化をしない
* 関係のないリファクタリングをしない
* 実行していないテストを「成功した」と報告しない
* 不確実な内容を断定しない

## 推奨プロンプト

### 最初に構想を整理する

```text
$lean-sdd shape

[作りたいアプリの概要]

分析結果をチャットに表示するだけでなく、
現在のワークスペースに以下のファイルを作成または更新してください。

- docs/product.md
- docs/roadmap.md

アプリケーションコードは変更しないでください。
最後に作成したファイル一覧を報告してください。
```

### 最初の実装を始める

```text
$lean-sdd start

docs/product.md と docs/roadmap.md を基に、
最初の垂直スライスを仕様化して実装してください。

実装前に以下を提示してください。

- 最初に実装するスライス
- 作成または更新するSpec
- 受け入れ条件
- 変更予定ファイル
- テスト方針
- リスク
```

### 次の機能を追加する

```text
$lean-sdd slice

[追加したい機能]

既存の docs/product.md、docs/roadmap.md、docs/decisions.md、
関連Specを確認した上で、
必要なSpecを作成または更新してから実装してください。

最小差分で実装し、受け入れ条件に対応するテストも追加してください。
```

### 仕様変更する

```text
$lean-sdd change

[変更したい内容]

既存Specを先に更新し、
その差分に合わせて実装とテストを変更してください。
関係のないリファクタリングは行わないでください。
```

### 整合性を確認する

```text
$lean-sdd check

docs/product.md、docs/roadmap.md、docs/specs、
実装、テストの整合性を確認してください。

ファイルは変更せず、
不一致、リスク、最小の修正案を報告してください。
```

## `shape` でファイルが作られない場合

`shape` は、通常 `docs/product.md` と `docs/roadmap.md` を作成または更新する想定です。

ファイルが作られない場合は、次を確認します。

* Codexの権限が `read-only` になっていないか
* 作業ディレクトリが想定のワークスペースか
* `shape` の指示が「提案だけ」になっていないか
* Skillの `Shape mode` に「ファイルを作成する」と明記されているか

明示的に実行する場合:

```text
$lean-sdd shape

[アプリの概要]

チャット上の提案だけで終わらせず、
現在のワークスペースに以下を実際に作成または更新してください。

- docs/product.md
- docs/roadmap.md

保存後、ファイルが存在することを確認してください。
```

## 関連Skill

### project-maintenance

既にある程度完成しているプロジェクトに、後から軽量Specや保守用ドキュメントを導入するためのSkillです。

使い分け:

* 新規開発: `lean-sdd`
* 既存保守: `project-maintenance`

## メンテナンス方針

このSkillは固定された完成品ではなく、自分の開発スタイルに合わせて育てます。

実際に使ってみて、以下のような失敗があれば `SKILL.md` に反映します。

* Codexがファイルを書かなかった
* 余計な実装をした
* Specが長くなりすぎた
* MVP全体を一気に作ろうとした
* テスト結果を曖昧に報告した
* docsと実装の整合性確認が弱かった

改善は、まずREADMEではなく `SKILL.md` に反映します。
READMEは使い方の説明、`SKILL.md` はCodexへの実行指示です。
